# Участник 4: каркас, история и отчёты

Ответственность: общий каркас проекта, модуль `reporting`, страница истории и отчётов, общие диаграммы, итоговая сборка документации.

## Выполненные функции

- Общий каркас: Maven Wrapper, `pom.xml`, `SportRentApplication`, `application.properties`, общие модели, DTO, интерфейсы модулей, единый формат ошибок (`shared/**`), главная страница, `common.css`, `api.js`. Каркас опубликован отдельным коммитом до начала работы остальных.
- История: список аренд от новых к старым, фильтр по статусу (`ACTIVE` / `COMPLETED`), подробности одной аренды.
- Сводка: общее число аренд, активные, завершённые и сумма стоимости всех оформленных аренд.
- Экспорт: скачивание подробного TXT-отчёта в UTF-8.
- Общие диаграммы (`docs/diagrams/class-diagram.puml`, `rental-creation-sequence.puml`) и общая таблица паттернов (`docs/patterns.md`).
- README с фактической инструкцией запуска.

## Маршруты модуля

| Маршрут | Ответ |
|---|---|
| `GET /api/rentals?status=ACTIVE` | список аренд, новые первыми; без `status` возвращает все |
| `GET /api/rentals/{id}` | подробности; 404 `RENTAL_NOT_FOUND`, если аренды нет |
| `GET /api/reports/summary` | сводка |
| `GET /api/reports/rentals.txt` | TXT-файл `sportrent-rentals.txt` (скачивание) |

Некорректный `status` или `id`, который не является UUID, возвращает 400 `INVALID_PARAMETER` в общем формате ошибок.

## Паттерн 1: Facade

**Проблема.** Чтобы показать историю или отчёт, нужно прочитать аренды из репозитория, отфильтровать по статусу, отсортировать, посчитать сводку и запустить экспорт. Если этим занимается контроллер, он зависит от репозитория, правил сортировки, арифметики сводки и экспортёра, и эта логика размазывается по коду.

**Решение.** `RentalReportFacade` реализует общий интерфейс `RentalQueryService` и скрывает всю подсистему за четырьмя методами. `RentalQueryController` знает только интерфейс `RentalQueryService`.

| Метод фасада | Что объединяет |
|---|---|
| `findRentals(status)` | чтение из `RentalRepository`, фильтр по статусу, сортировка по `createdAt` от новых к старым |
| `getRental(id)` | поиск аренды и ошибка 404, если её нет |
| `getSummary()` | подсчёт активных и завершённых, сумма `priceBreakdown.total()` по всем арендам, округление до 2 знаков |
| `buildTextReport()` | получение отсортированного списка, расчёт сводки, время формирования из `Clock`, запуск `TextReportExporter` |

Это не пустая обёртка: фасад содержит логику фильтрации, сортировки, расчёта сводки и порядка вызова экспортёра, которой нет ни в контроллере, ни в репозитории.

**Классы.** `RentalQueryService` (интерфейс в `shared/contract`), `RentalReportFacade`, `RentalQueryController`, `TextReportExporter`, `ClockConfig` (бин `Clock`, чтобы время отчёта можно было подменить в тесте).

## Паттерн 2: Visitor

**Проблема.** Отчёт нужно уметь формировать из разных частей аренды (сама аренда, снимок предмета, разбивка цены). Если положить форматирование в модели, они начнут знать про текст отчёта, а новый формат (например, CSV) придётся добавлять в каждую модель.

**Решение.** Модели только принимают посетителя, форматирование находится в посетителе.

- `ReportElement` с методом `accept(ReportVisitor)`: реализуют `Rental`, `EquipmentSnapshot`, `PriceBreakdown`.
- `ReportVisitor` с отдельными методами `visit(Rental)`, `visit(EquipmentSnapshot)`, `visit(PriceBreakdown)`.
- `Rental.accept()` посещает саму аренду, затем `equipmentSnapshot.accept(visitor)` и `priceBreakdown.accept(visitor)`. Обход реально проходит через accept/visit, без `instanceof`.
- `TextReportVisitor` формирует текст: клиент, даты, срок, тариф, услуги, предмет на момент оформления, разбивка цены с точными суммами.
- `TextReportExporter` собирает заголовок и сводку и для каждой аренды вызывает `rental.accept(visitor)`.

**Почему это Visitor, а не просто форматирование.** Обход выполняется двойной диспетчеризацией: элемент вызывает `visitor.visit(this)` с конкретным типом. Чтобы добавить новый формат, достаточно нового класса, реализующего `ReportVisitor`; модели `Rental`, `EquipmentSnapshot`, `PriceBreakdown` не меняются.

## Как показать через интерфейс

1. Запустить `.\mvnw.cmd spring-boot:run` и открыть `http://localhost:8080`.
2. В «Аренды» оформить две аренды разных предметов; одну вернуть.
3. Открыть «История и отчёты». Проверить сводку, список от новых к старым, фильтр «Активные» / «Завершённые».
4. Нажать «Подробнее»: видны клиент, снимок предмета и разбивка цены.
5. Нажать «Скачать TXT-отчёт» и открыть файл: сводка, затем аренды; суммы в тексте совпадают со страницей.
6. Для Visitor показать `TextReportVisitor` и `Rental.accept()`: модель не содержит текста отчёта.

## Ограничения

- Отчёт собирается в памяти одной строкой; для очень большой истории потребовалась бы потоковая запись.
- История и сводка читают все аренды целиком; пагинации нет.
- «Сумма оформленных аренд» это не выручка: учёт оплаты в проекте не ведётся. Это написано на странице и в отчёте.
- Экспорт только в TXT. Даты в отчёте в формате ISO-8601 (UTC).
- У Visitor есть известный компромисс: новый тип элемента потребует нового метода `visit` во всех посетителях.

## Пример небольшого изменения на защите

1. **Новый формат (Visitor).** Добавить `CsvReportVisitor implements ReportVisitor` в `reporting`: три метода `visit` пишут строки через запятую. Модели не меняются, это показывает суть паттерна.
2. **Изменить порядок истории (Facade).** В `RentalReportFacade.findRentals` убрать `.reversed()` из компаратора: история пойдёт от старых к новым. Контроллер и страница не меняются, потому что правило сортировки скрыто в фасаде.
3. **Добавить строку в отчёт.** В `TextReportVisitor.visit(Rental)` добавить `line("Предмет: " + rental.equipmentId());`. Меняется только посетитель.
